# Agentic AI — Model, Tool Calling, Workflows & LangGraph

## 1. How to Build an Agent

To build an Agent, we need:

```text
Agent
│
├── Model + Prompt
├── Tool
└── Framework
```

* The model helps the Agent understand the goal and decide what needs to happen.

* The tool performs the required action.

* The framework helps connect and manage the model, tools, and workflow.

---

# 2. Model

When building an Agent, we need access to a model.

There are different ways to get access to models.

### Model Access

```text
Model
│
├── Hosted by Model Provider
│
├── Hosted by Cloud Provider
│
└── Self Hosted
```

### Hosted by Model Provider

Example:

* Google AI Studio

Free access may be available depending on the provider/service.

### Hosted by Cloud Providers

Cloud providers can provide models for enterprise use.

### Self Hosted

The organization hosts and manages the model itself.

# 8. Why Do We Need Tools?

A model can generate content such as:

* Text
* Code
* Images
* Music
* Video

But generating content is different from performing an external action.

For example, suppose the user says:

```text
Send "How are you?"
to test@gmail.com
```

The model can understand the request and generate a tool-call request.

But the actual email-sending operation is performed by the **tool**.

So:

```text
Model
 ↓
Requests tool call
 ↓
Tool
 ↓
Performs action
```

### Important

> **Model → decides/request the action**

> **Tool → performs the action**

---

# 9. Tool Calling

Models can be trained to help determine which available tool should be called.

This ability is called:

> **Tool Calling**

Example:

```text
User
 ↓
"Send how are you email to test@gmail.com"
 ↓
Model
 ↓
Tool Call
 ↓
send_email
```

The model can provide the arguments required by the tool:

```text
destination = test@gmail.com
content = How are you?
```

---

# 10. What Happens During Tool Calling?

Today's class showed the actual messages exchanged while building an Agent.

The flow is:

```text
User
 ↓
Model
 ↓
Tool Call
 ↓
Framework
 ↓
Tool
 ↓
Tool Result
 ↓
Framework
 ↓
Model
 ↓
Final Response
```

Let's understand each step.

---

## Step 1 — User Gives the Goal

The user provides the request:

```text
Send "How are you?"
email to test@gmail.com
```

This is the initial goal.

---

## Step 2 — Model Decides to Call a Tool

The model understands the request and generates a tool-call request.

Conceptually:

```text
Tool:
send_email

Arguments:
destination = test@gmail.com
content = How are you?
```

Important:

> The model has **requested the tool call**. It has not itself performed the email-sending action.

---

## Step 3 — Framework Calls the Tool

The framework receives the model's tool-call request.

```text
Model
 ↓
Tool Call
 ↓
Framework
 ↓
Tool
```

The framework invokes the appropriate tool and passes the required arguments.

---

## Step 4 — Tool Performs the Action

The `send_email` tool performs the actual operation.

For example:

```text
send_email(
    destination="test@gmail.com",
    content="How are you?"
)
```

The tool then produces a result.

```text
Email sent successfully
```

---

## Step 5 — Framework Passes the Result Back

The framework passes the tool result back to the model.

```text
Tool
 ↓
Tool Result
 ↓
Framework
 ↓
Model
```

---

## Step 6 — Model Generates Final Response

The model understands the tool result and generates the final response:

```text
OK. I've sent the email to test@gmail.com.
```

### Complete Flow

```text
                    USER
                      ↓
                    Goal
                      ↓
                  ┌───────┐
                  │ Model │
                  └───┬───┘
                      ↓
                  Tool Call
                      ↓
                ┌───────────┐
                │ Framework │
                └─────┬─────┘
                      ↓
                  ┌──────┐
                  │ Tool │
                  └──┬───┘
                     ↓
                Tool Result
                     ↓
                ┌───────────┐
                │ Framework │
                └─────┬─────┘
                      ↓
                  ┌───────┐
                  │ Model │
                  └───┬───┘
                      ↓
               Final Response
```

# 11. Model vs Tool vs Framework

Keep these responsibilities clear.

| Component     | Main responsibility                                                  |
| ------------- | -------------------------------------------------------------------- |
| **Model**     | Understands the request and generates a response/tool-call request   |
| **Prompt**    | Gives instructions and context to the model                          |
| **Tool**      | Performs an action                                                   |
| **Framework** | Connects and manages the model, tools, workflow and other components |
| **Agent**     | Overall system that uses these components to accomplish a task       |

### Simple memory

```text
Model
 ↓
Reason / Decide
 ↓
Tool Call
 ↓
Framework
 ↓
Tool
 ↓
Action
```

# 12. Static Steps

A workflow can have **Static Steps**.

Static Steps mean that the workflow has a fixed set of steps and conditional logic determines which node should be called.

The class refers to this as:

> **Router**

Example:

```text
Input
 ↓
Router
 ├── Condition A → Node A
 ├── Condition B → Node B
 └── Condition C → Node C
```

The developer defines the possible workflow.

---

# 13. Dynamic Steps

Dynamic Steps are different.

In Dynamic Steps:

> **The LLM decides the steps.**

The class refers to this as:

> **Autonomous Agent**

Example:

```text
Goal
 ↓
LLM
 ↓
Decides next step
 ↓
Tool / Node
 ↓
Result
 ↓
LLM
 ↓
Decides next step
```

The workflow is not completely fixed beforehand.

---

# 14. Static vs Dynamic Steps

| Static Steps                   | Dynamic Steps                           |
| ------------------------------ | --------------------------------------- |
| Fixed workflow                 | Dynamic workflow                        |
| Developer defines the flow     | LLM decides the steps                   |
| Uses routing/conditional logic | Autonomous Agent                        |
| More controlled                | Less predictable/reliable               |
| Steps are defined beforehand   | Steps can change based on the situation |

### Easy way to remember

> **Static → Developer decides the flow**

> **Dynamic → LLM decides the flow**

---

# 15. Problem with Dynamic Steps

The class points out:

> **Dynamic steps have very less reliability.**

The reason is that the LLM is deciding the steps dynamically.

The system therefore needs ways to provide more control over the workflow.

This leads us to:

> **LangGraph**

---

# 16. LangGraph

LangGraph was introduced in the class to help build and control agent workflows.

The class mentions that LangGraph provides:

* Human in the loop
* Persistence
* Tools
* LLM
* State

The main LangGraph concepts introduced are:

```text
Node
Edge
State
Graph
```

---

# 17. Node

A Node can be any computation in the workflow.

Examples:

* Interacting with an LLM
* Calling a tool
* Retrieving data from a vector store

```text
Node
│
├── LLM interaction
├── Tool call
└── Data retrieval
```

---

# 18. Edge

An Edge is the connection between nodes.

Example:

```text
Node A
  ↓
Edge
  ↓
Node B
```

The edge determines how the workflow moves between nodes.

---

# 19. State

State is:

> **Common data that is accessible to all the nodes when they are executing.**

Nodes can change the state.

Conceptually:

```text
             State
          ┌────┼────┐
          ↓    ↓    ↓
        Node  Node  Node
          A    B     C
```

The nodes can access the shared state while executing.

---

# 20. Graph

A Graph is a workflow defined using:

> **Nodes + Edges + State**

```text
Graph
│
├── Nodes
├── Edges
└── State
```

Example:

```text
       ┌─────────┐
       │ Node A  │
       └────┬────┘
            ↓
       ┌─────────┐
       │ Node B  │
       └────┬────┘
            ↓
       ┌─────────┐
       │ Node C  │
       └─────────┘

       Shared State
```

---

# 21. LangGraph Mental Model

The easiest way to remember the concept:

```text
LangGraph
    ↓
Graph
    ↓
Nodes + Edges + State
```

Where:

```text
Node  → Computation

Edge  → Connection

State → Shared data

Graph → Complete workflow
```
