# 1. Introduction to Helm

Helm is the **package manager for Kubernetes**.

Think of it as:

| Technology | Package Manager |
|------------|-----------------|
| Ubuntu | apt |
| RHEL | yum / dnf |
| Python | pip |
| Node.js | npm |
| Kubernetes | Helm |

Instead of manually applying dozens of YAML files, Helm packages them into reusable units called **Charts**.

---

# 2. Why Helm?

Imagine deploying a production application.

Without Helm:

```
Deployment.yaml
Service.yaml
Ingress.yaml
ConfigMap.yaml
Secret.yaml
PVC.yaml
ServiceAccount.yaml
Role.yaml
RoleBinding.yaml
NetworkPolicy.yaml
HorizontalPodAutoscaler.yaml
```

You might have to manage 10–50 YAML files manually.

With Helm:

```
helm install my-app ./chart
```

One command installs the entire application.

---

# 3. Problems Before Helm

Without Helm:

```
Developer

↓

Creates 30 YAML files

↓

Copies files

↓

Edits manually

↓

Makes mistakes

↓

Different environments drift
```

Common issues:

- Duplicate YAML
- Configuration drift
- Manual edits
- Difficult upgrades
- Inconsistent deployments

Helm addresses these by packaging resources and using templates with configurable values.

---

# 4. Helm Architecture

```
            Developer
                 │
                 ▼
          helm install
                 │
                 ▼
          Helm Client
                 │
                 ▼
      Kubernetes API Server
                 │
                 ▼
          Kubernetes Cluster
```

Modern Helm (v3+) is **client-side** and communicates directly with the Kubernetes API server. Earlier versions used a server-side component called **Tiller**, but **Tiller was removed in Helm 3**.

# 13. Helm Template Engine

Helm uses the **Go Template** engine.

Instead of writing static YAML, you write templates that are rendered into Kubernetes manifests.

Example:

```yaml
replicas: {{ .Values.replicaCount }}
```

If:

```yaml
replicaCount: 3
```

The rendered YAML becomes:

```yaml
replicas: 3
```

---

# Rendering Flow

```
values.yaml

        │

        ▼

Helm Template Engine

        │

        ▼

deployment.yaml

        │

        ▼

Rendered Kubernetes YAML

        │

        ▼

API Server
```

---

# 14. Template Variables

Access values from `values.yaml`.

Example:

```yaml
image:
  repository: nginx
  tag: "1.27"
```

Template:

```yaml
image:

  repository: {{ .Values.image.repository }}

  tag: {{ .Values.image.tag | quote }}
```

Rendered:

```yaml
image:
  repository: nginx
  tag: "1.27"
```

---

## Common Variables

| Expression | Description |
|------------|-------------|
| `.Values` | User values |
| `.Release.Name` | Release name |
| `.Release.Namespace` | Target namespace |
| `.Chart.Name` | Chart name |
| `.Chart.Version` | Chart version |

---

# Example

```yaml
metadata:

  name: {{ .Release.Name }}
```

Install:

```bash
helm install payment ./chart
```

Result:

```yaml
metadata:

  name: payment
```

---

# 15. Built-in Objects

Helm exposes useful runtime information.

Example:

```yaml
metadata:

  labels:

    app: {{ .Chart.Name }}

    version: {{ .Chart.Version }}

    release: {{ .Release.Name }}
```

Rendered automatically during installation.

# 16. Pipelines & Functions

Go templates support pipelines.

Example:

```yaml
{{ .Values.image.tag | quote }}
```

Meaning:

```
image.tag

↓

quote()

↓

"1.27"
```

---

## Useful Functions

| Function | Purpose |
|----------|---------|
| `quote` | Wrap value in quotes |
| `upper` | Uppercase |
| `lower` | Lowercase |
| `default` | Default value |
| `trim` | Remove whitespace |
| `replace` | Replace text |

---

## Example

```yaml
imagePullPolicy:

{{ .Values.pullPolicy | default "IfNotPresent" }}
```

If the user doesn't provide `pullPolicy`, the rendered value is:

```yaml
imagePullPolicy: IfNotPresent
```

---

# 17. Conditional Logic

Use `if` to render resources only when needed.

Example:

```yaml
{{- if .Values.ingress.enabled }}

apiVersion: networking.k8s.io/v1
kind: Ingress

...

{{- end }}
```

Values:

```yaml
ingress:

  enabled: true
```

Ingress is rendered.

If:

```yaml
enabled: false
```

No Ingress manifest is generated.

---

# 18. Loops (`range`)

Generate repeated sections dynamically.

Example values:

```yaml
ports:

- 80

- 443
```

Template:

```yaml
ports:

{{- range .Values.ports }}

- containerPort: {{ . }}

{{- end }}
```

Rendered:

```yaml
ports:

- containerPort: 80

- containerPort: 443
```

---

# 19. Named Templates & `_helpers.tpl`

Avoid repeating common snippets.

Example:

```gotemplate
{{- define "my-app.labels" }}

app.kubernetes.io/name: {{ .Chart.Name }}

app.kubernetes.io/instance: {{ .Release.Name }}

{{- end }}
```

Use it:

```yaml
metadata:

  labels:

{{ include "my-app.labels" . | indent 4 }}
```

Benefits:

- Reusable
- Consistent
- Easier maintenance

---

# 20. Values Precedence

Helm resolves values in this order (highest priority first):

1. `--set`
2. `--values` / `-f`
3. Chart `values.yaml`

Example:

Chart:

```yaml
replicaCount: 2
```

Environment file:

```yaml
replicaCount: 3
```

Command:

```bash
helm install app ./chart \
  --set replicaCount=5
```

Result:

```text
replicaCount = 5
```

---

# 21. Chart Dependencies

One chart can depend on another.

Example:

```
Application

↓

Redis

↓

PostgreSQL
```

`Chart.yaml`

```yaml
dependencies:

- name: redis

  version: "20.x.x"

  repository: https://charts.bitnami.com/bitnami
```

Fetch dependencies:

```bash
helm dependency update
```

Dependencies are stored in the chart's `charts/` directory.

# 24. Release Lifecycle

A Helm release goes through several stages.

```
Chart

↓

Install

↓

Release

↓

Upgrade

↓

Rollback (if required)

↓

Uninstall
```

Each installation creates a unique release record.

---

# View Releases

```bash
helm list
```

Example:

```
NAME        NAMESPACE   STATUS     CHART
payment     default     deployed   payment-1.0.0
```

---

# Release Details

```bash
helm status payment
```

Useful information includes:

- Release status
- Namespace
- Revision
- Last deployment time
- Managed resources

---

# 25. Upgrades

Helm upgrades an existing release while preserving release history.

Upgrade:

```bash
helm upgrade payment ./payment-chart
```

Upgrade with new values:

```bash
helm upgrade payment ./payment-chart \
  -f values-prod.yaml
```

Override values:

```bash
helm upgrade payment ./payment-chart \
  --set replicaCount=5
```

---

## Preview Changes

Render locally:

```bash
helm template payment ./payment-chart
```

Validate without applying:

```bash
helm upgrade payment ./payment-chart \
  --dry-run --debug
```

For change visualization, many teams also use the `helm diff` plugin before upgrades.

---

# 26. Rollbacks

If an upgrade introduces problems:

```
Version 1

↓

Version 2

↓

Application Failure

↓

Rollback

↓

Version 1 Restored
```

View history:

```bash
helm history payment
```

Rollback:

```bash
helm rollback payment 1
```

Where `1` is the revision number.

# 28. Helm Hooks

Hooks execute Kubernetes resources at specific lifecycle events.

Examples:

```
Pre-install

↓

Create Database

↓

Install Application
```

---

## Hook Types

| Hook | When It Runs |
|------|--------------|
| pre-install | Before installation |
| post-install | After installation |
| pre-upgrade | Before upgrade |
| post-upgrade | After upgrade |
| pre-delete | Before uninstall |
| post-delete | After uninstall |
| test | During `helm test` |

---

## Example

```yaml
metadata:

  annotations:

    "helm.sh/hook": pre-install
```

Typical uses:

- Database migrations
- Backup Jobs
- Validation Jobs
- Initialization tasks

# 29. OCI Registries

Modern Helm supports storing charts in OCI-compatible registries.

Examples:

- OCI registry provided by cloud platforms
- Container registries that support OCI artifacts

Login:

```bash
helm registry login registry.example.com
```

Pull:

```bash
helm pull oci://registry.example.com/charts/payment
```

Push:

```bash
helm push payment-1.0.0.tgz \
oci://registry.example.com/charts
```

OCI is increasingly preferred over traditional chart repositories.

# 32. Production Best Practices

---

## Use Version Control

Store:

- Charts
- Values files

in Git.

---

## Separate Values

```
values-dev.yaml

values-test.yaml

values-prod.yaml
```

Never hardcode environment-specific configuration into templates.

---

## Avoid Secrets in Values Files

Prefer:

- External Secrets Operator
- Cloud secret managers
- Sealed Secrets

rather than committing sensitive values to Git.

---

## Validate First

```bash
helm lint .

helm template .

helm upgrade --dry-run --debug
```

---

## Prefer OCI Registries

OCI provides a standardized way to distribute charts alongside container artifacts.

---

## Pin Chart Versions

Avoid deploying floating versions in production.

Explicit version pinning improves reproducibility.
