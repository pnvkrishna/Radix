# 1. Introduction

Imagine a company with different teams:

- Developers
- QA Engineers
- DevOps Engineers
- Security Team
- Platform Administrators

Should everyone have permission to delete namespaces?

```
NO
```

Should everyone be allowed to read logs?

```
Maybe
```

Should everyone be able to modify Secrets?

```
NO
```

Kubernetes solves this using **Role-Based Access Control (RBAC).**

---

# 2. Authentication vs Authorization

These are two different concepts.

---

## Authentication

Authentication answers:

```
Who are you?
```

Examples:

- Client certificate
- Token
- OpenID Connect (OIDC)
- Cloud IAM integration

Result:

```
Identity Verified
```

---

## Authorization

Authorization answers:

```
What are you allowed to do?
```

Examples:

- Read Pods
- Create Deployments
- Delete Services
- View Secrets

RBAC is an **authorization** mechanism.

---

## Flow

```
User

↓

Authentication

↓

Identity Confirmed

↓

Authorization (RBAC)

↓

Allow or Deny

↓

Kubernetes API
```

---

# 3. What is RBAC?

RBAC controls access to Kubernetes resources.

Instead of giving every user full access, permissions are assigned through roles.

Example:

```
Developer

↓

Read Pods

Create Deployments

View Logs

------------

Cannot

Delete Nodes

Modify Cluster Configuration
```

---

# Benefits

- Security
- Least privilege
- Auditing
- Multi-team support
- Regulatory compliance

---

# 4. RBAC Components

RBAC consists of four primary resources.

```
Role

↓

Defines Permissions

------------

ClusterRole

↓

Defines Cluster-Wide Permissions

------------

RoleBinding

↓

Assigns Role

------------

ClusterRoleBinding

↓

Assigns ClusterRole
```

---

## Relationship

```
User / Group / ServiceAccount

↓

Binding

↓

Role or ClusterRole

↓

Permissions
```

# 5. ServiceAccounts

Applications running inside Kubernetes do not normally authenticate as human users.

They use **ServiceAccounts**.

Example:

```
Application Pod

↓

ServiceAccount

↓

Kubernetes API
```

---

## Default ServiceAccount

Every namespace automatically includes:

```
default
```

Example:

```bash
kubectl get serviceaccounts
```

Output:

```
NAME      SECRETS   AGE
default   ...       ...
```

---

## Create a ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount

metadata:
  name: payment-sa
```

Create:

```bash
kubectl apply -f sa.yaml
```

---

## Use the ServiceAccount

```yaml
spec:

  serviceAccountName: payment-sa
```

Now the Pod uses:

```
payment-sa
```

instead of the default ServiceAccount.

---

# Production Recommendation

Avoid using the default ServiceAccount for production workloads.

Create dedicated ServiceAccounts with only the permissions each application requires.

---

# 6. Roles

A **Role** defines permissions **within a single namespace**.

Example:

```
Namespace

↓

development

↓

Role

↓

Read Pods
```

---

## Role YAML

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role

metadata:
  name: pod-reader
  namespace: development

rules:

- apiGroups: [""]

  resources:

  - pods

  verbs:

  - get
  - list
  - watch
```

---

# YAML Explained

## apiGroups

Core resources (Pods, Services, ConfigMaps, Secrets) use:

```yaml
apiGroups: [""]
```

---

## resources

Specifies the resource type.

Example:

```yaml
pods
```

---

## verbs

Allowed operations.

Examples:

```
get
list
watch
create
update
patch
delete
```

---

# Example

This Role allows:

```
Pods

↓

Read Only
```

within the `development` namespace.

---

# 7. ClusterRoles

Some resources are cluster-wide.

Examples:

- Nodes
- PersistentVolumes
- Namespaces
- Cluster-wide APIs

For these, use a **ClusterRole**.

---

## ClusterRole YAML

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole

metadata:
  name: node-reader

rules:

- apiGroups: [""]

  resources:

  - nodes

  verbs:

  - get
  - list
  - watch
```

---

# Difference

| Role | ClusterRole |
|------|-------------|
| Namespace-scoped | Cluster-scoped |
| Access within one namespace | Can grant cluster-wide permissions |
| Used with RoleBinding | Used with ClusterRoleBinding (or RoleBinding for namespace-scoped access to the listed resources) |

---

## Production Examples

Role:

```
Developer

↓

Read Pods

Namespace Only
```

ClusterRole:

```
Platform Team

↓

Read Nodes

Entire Cluster
```

# 9. RoleBinding

A **Role** defines permissions.

A **RoleBinding** assigns those permissions to a user, group, or ServiceAccount.

Without a RoleBinding:

```
Role Exists

↓

Nobody Can Use It
```

---

## Relationship

```
Role

↓

RoleBinding

↓

User / Group / ServiceAccount

↓

Permissions Granted
```

---

## RoleBinding YAML

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding

metadata:
  name: developer-binding
  namespace: development

subjects:

- kind: ServiceAccount

  name: payment-sa

  namespace: development

roleRef:

  apiGroup: rbac.authorization.k8s.io

  kind: Role

  name: pod-reader
```

---

## YAML Explained

### subjects

Specifies **who** receives the permissions.

Possible values:

- User
- Group
- ServiceAccount

---

### roleRef

Specifies **which Role** is assigned.

---

## Result

```
payment-sa

↓

RoleBinding

↓

pod-reader

↓

Read Pods
```

---

# 10. ClusterRoleBinding

A **ClusterRoleBinding** grants a **ClusterRole** to one or more subjects.

Example:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding

metadata:
  name: node-reader-binding

subjects:

- kind: User

  name: alice

roleRef:

  apiGroup: rbac.authorization.k8s.io

  kind: ClusterRole

  name: node-reader
```

---

## Result

```
Alice

↓

ClusterRoleBinding

↓

node-reader

↓

Read Nodes
```

---

## Important Note

A **ClusterRole** can also be referenced from a **RoleBinding**.

This grants the ClusterRole's permissions **only within that namespace** (for namespace-scoped resources).

This is a common production pattern.

---

# 11. Users, Groups & ServiceAccounts

RBAC can grant permissions to different subjects.

| Subject | Typical Use |
|---------|-------------|
| User | Human administrator or developer |
| Group | Team (e.g., developers, QA, operations) |
| ServiceAccount | Application running inside the cluster |

---

## Example

```
Developers Group

↓

RoleBinding

↓

Developer Role

↓

Development Namespace
```

Applications:

```
Application

↓

ServiceAccount

↓

RoleBinding

↓

API Access
```

# 12. kubectl auth can-i

This is one of the most useful RBAC troubleshooting commands.

---

## Check Your Own Permissions

```bash
kubectl auth can-i create pods
```

Example output:

```
yes
```

or

```
no
```

---

## Check Another Action

```bash
kubectl auth can-i delete deployments
```

---

## Check Namespace

```bash
kubectl auth can-i get pods \
--namespace=production
```

---

## Check a ServiceAccount

```bash
kubectl auth can-i get secrets \
--as=system:serviceaccount:development:payment-sa \
--namespace=development
```

---

## List Permissions

```bash
kubectl auth can-i --list
```

This displays the effective permissions for the current identity.

---

# 13. Impersonation

Administrators can test permissions without logging in as another identity.

Example:

```bash
kubectl auth can-i list pods \
--as=alice \
--namespace=development
```

ServiceAccount example:

```bash
kubectl auth can-i get configmaps \
--as=system:serviceaccount:development:payment-sa
```

---

## Why Use Impersonation?

- Verify RBAC changes
- Troubleshoot access issues
- Test CI/CD permissions
- Validate ServiceAccount access

Always ask:

```
What is the minimum permission required?
```

Example:

Instead of:

```

*

*
```

```yaml

- pods

verbs:

- get
- list

```

# 17. Common RBAC Mistakes

---

## Mistake 1

Using:

```
cluster-admin
```

for every user or application.

Problem:

```
Application

↓

Compromised

↓

Full Cluster Access
```

Always create the smallest permission set that satisfies the workload.

---

## Mistake 2

Using the default ServiceAccount.

```
default

↓

Many Applications

↓

Shared Identity
```

Instead:

```
payment-sa

order-sa

inventory-sa
```

Each application should have its own ServiceAccount.

---

## Mistake 3

Using wildcards.

Avoid:

```yaml
resources:
- "*"

verbs:
- "*"
```

Instead specify only:

- Required resources
- Required verbs

---

## Mistake 4

Granting Secret access unnecessarily.

Secrets often contain:

- Database passwords
- API keys
- Certificates
- Tokens

Only trusted workloads and administrators should have access.

---

## Mistake 5

Not reviewing old bindings.

Users leave teams.

Applications are retired.

Review:

- RoleBindings
- ClusterRoleBindings

regularly.


---

## Step 4

Describe the binding

```bash
kubectl describe rolebinding developer-binding
```

or

```bash
kubectl describe clusterrolebinding node-reader-binding
```

Verify:

- Subject
- Role reference
- Namespace

---

## Step 5

Inspect the Role

```bash
kubectl describe role pod-reader
```

or

```bash
kubectl describe clusterrole node-reader
```

Check:

- Resources
- Verbs
- API Groups

# 20. Aggregated ClusterRoles

Kubernetes supports **ClusterRole aggregation**.

Multiple ClusterRoles can automatically contribute rules to another ClusterRole based on labels.

Example:

```
ClusterRole A

↓

Aggregate

↓

admin
```

Example label:

```yaml
metadata:

  labels:

    rbac.authorization.k8s.io/aggregate-to-admin: "true"
```

Use this feature when extending the built-in `admin`, `edit`, or `view` roles in a controlled way.

# 21. Production Best Practices

---

## One ServiceAccount Per Application

```
Frontend

↓

frontend-sa

----------------

Backend

↓

backend-sa
```

Never share identities unnecessarily.

---

## Follow Least Privilege

Grant only:

- Required resources
- Required verbs
- Required namespaces

---

## Prefer Groups for Human Users

```
Developers

↓

Group

↓

RoleBinding
```

Managing groups is simpler than binding permissions to each individual user.

---

## Audit Regularly

Review:

- Roles
- ClusterRoles
- RoleBindings
- ClusterRoleBindings

Remove unused access promptly.

---

## Avoid Long-Lived Credentials

Where possible, integrate with:

- OIDC
- Cloud IAM
- Short-lived tokens

rather than distributing long-lived static credentials.
